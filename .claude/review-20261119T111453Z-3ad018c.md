## 指摘

### 1. 日時形式の検査が依存パッケージの有無で黙って無効になる（重要）

- 対象: `validation/check.py:28-30`、`validation/check.py:341-344`、`examples/validation.md:7`
- 根拠: jsonschema の `format: "date-time"` の検査には `rfc3339-validator` が必要。未導入の場合、`FORMAT_CHECKER` は警告を出さずにこの形式をスキップする。`examples/validation.md:7` では「日時形式検査を有効にする」としているが、回帰検証には日時形式の拒否例がない。そのため、形式検査が働いていなくても検証は成功する。
- 再現条件: `rfc3339-validator` がない環境で、`履歴[0].時刻` を `2026-11-01T12:00:00`（オフセットなし）または `2026-11-01`（日付のみ）にする。
- 影響: スキーマ検査を通過した後、`check_history` の時刻比較で `TypeError: can't compare offset-naive and offset-aware datetimes` が発生し、トレースバックで終了する。終了コードは1なので不適合としては扱われるが、`check_local_record` の分類済みメッセージは出ない。また、この比較に到達しない日時欄（例：証拠の `取得` を模擬記録で使う場合）では、不正な日時がそのまま受理される。
- 修正案:
  - 検証を始める前に、`date-time` の検査が有効であることを確かめる。不正な日時を1件検査して拒否されなければ停止する。
  - 回帰検証に、オフセットなしの日時と日付のみの日時の拒否例を加える。
  - 必要な依存として `jsonschema[format]` または `rfc3339-validator` を明記する。
  - あわせて、`parse_time` がオフセットなしの日時を受け取ったら `AssertionError` か `ValueError` にする。

### 2. 有効な RFC 3339 日時の一部が「解析に失敗」として拒否される（軽微）

- 対象: `validation/check.py:145-146`、`validation/check.py:356-357`
- 根拠: `datetime.fromisoformat` は、RFC 3339 で許されるうるう秒（`:60`）や、マイクロ秒を超える小数秒を解析できない。
- 再現条件: `履歴[0].時刻` を `2026-11-01T00:00:60Z` にする。
- 影響: 結果は `記録の読み取りまたは解析に失敗: ValueError` となり、記録が不適合なのか検査器の制約なのかを区別できない。
- 修正案: これらの表記を受け付けないことを仕様に明記して、専用のメッセージで拒否する。または、小数秒を6桁に切り詰めて正規化する。

### 3. 模擬記録では履歴の `判断ID` の参照先を検査しない（軽微）

- 対象: `validation/check.py:92-93`、`validation/check.py:112-113`
- 根拠: `判断ID` の存在確認は `check_execution_authorization` の中だけで行われ、この関数は `区分 == "実運用"` の場合にしか呼ばれない。`examples/validation.md` の再検査手順は「IDの一意性と参照先」の確認を求めている。
- 再現条件: 模擬記録で、実行遷移の `判断ID` を存在しない値にする。検査は成功する。
- 影響: 模擬記録を実運用に切り替えるまで、参照切れが見つからない。
- 修正案: `check_history` で、`判断ID` がある場合は区分にかかわらず `decision_ids` に含まれることを確認する。

### 4. 合意の時刻同士の整合を、模擬記録と撤回について検査しない（軽微）

- 対象: `validation/check.py:116-124`
- 根拠: `発効 <= 期限` は実運用の実行遷移がある場合にだけ検査され、`発効 <= 撤回` はどの場合にも検査されない。
- 再現条件: 模擬記録で `合意.発効 = 2026-12-01T00:00:00Z`、`合意.撤回 = 2026-10-01T00:00:00Z` とする。期限は 2026-11-30 である。検査は成功する。
- 影響: 矛盾した合意の記録が受理され、実運用に転用すると判定の前提が崩れる。
- 修正案: 合意のすべての版について、`発効 <= 期限` と、撤回がある場合の `発効 <= 撤回` を区分にかかわらず検査する。

### 5. 回帰検証の一部で format_checker を指定していない（軽微）

- 対象: `validation/check.py:211`、`validation/check.py:251`、`validation/check.py:261`、`validation/check.py:265`
- 根拠: `Draft202012Validator(load(...)).validate(run)` は形式検査を伴わない。一方、`check_contract` と `check_local_record` は `FORMAT_CHECKER` を指定している。
- 影響: 反例の中で変更した日時が形式上不正でも検出されない。いまの反例はすべて正しい形式なので実害はない。
- 修正案: validator の生成を1か所にまとめる。

- 判断が `旧合意` の版を参照していて、その版が期限内で撤回されていない場合、改訂後でも実行遷移は受理される。`spec/workflow.md` は「参照先の合意が遷移時点に有効」としているが、改訂によって置き換えられた版が有効なのかは明記されていない。人間による判断の対象として記録する。
