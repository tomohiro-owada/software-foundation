# Software Foundation自身への適用

Goalは、既存のエージェントが事業の判断・証拠・引継ぎを再現できること。既存7文書を保全し、規範と実行記録を追加する案を選んだ。現状維持では事前条件や再開の検査手順が揃わず、専用エンジンは権限外。比較の結果、規範と記録契約を採用した。実運用での有効性と異なる企業のAIレビューは未確認。未決事項は人間の判断対象とする。PRの検証とマージの操作は人間の明示指示により委任された。

## 形式検証

JSON Schema Draft 2020-12と日時形式検査を有効にする。[契約の確認例](contract-run.json)は受理する。同じ記録から重要な判断を必須レビューなしで実行可にした例と、準備から運用に直接移る例を作り、拒否を確認する。

## 意味検査

- 課題が曖昧な場合、判断を変える対象者や工程を一問で特定する。Contextの各制約から品質目標と検証方法を導出する。
- 不作為を含む候補を比較し、決定時のGoal・Context・合意の版、根拠、レビューへの処置を残す。
- 成果物の適合とGoalへの寄与を評価する。稼働時間を費用に含め、仮定を変えて判断が逆転する境界を確認する。外部変化があっても従来の判定条件で再計算し、違う条件を使う場合は次の評価に適用する。
- 中断から戻る際は、入力の版、権限、副作用、次手を照合する。未知の重大リスクや権限外の操作があれば相談待ちにする。

再検査時は、履歴の先頭・連続性・時刻順と末尾の現在状態、IDの一意性と参照先、判断時点のGoal・Context・合意版を確認する。実運用の実行遷移は実行可の判断と突き合わせ、必須レビューの企業差、共有権限、各根拠、測定の事前確定、合意の有効期限を確認する。模擬証拠の実測への流用、予算超過、成功条件の事後変更を確認したら適合を保留する。構造検査だけでは参照先、レビューの真正性、測定の妥当性、因果関係を判定できない。

次に人間が判断するのは、重要判断の境界と別企業レビューの利用方法、案件ごとの評価条件、既存案件に適用する版。自動監視や実顧客での成功は未検証。

## PRと取り込み後の再検証

リポジトリのルートから `python validation/check.py` を実行する。Python 3、`jsonschema`、初回コミットを含むGit履歴が必要。この手順は契約のサンプル検証用で、各環境のAIエージェントは同等の検査を任意の手段で行える。

PRの先端コミットを検証し、差分の意味検査を行う。マージを人間から委任された場合は、検証したコミットを指定して取り込む。取り込み後は最新の基準ブランチを取得し、同じ検査を再実行する。失敗時は差分と原因を報告し、修正を次のPRで検証する。別企業レビューの実施状況は検証結果と併記する。

履歴の日時はオフセットを反映した時点で比較する。サンプル検証では、表記上は前後が逆でも順序が正しい履歴を受理し、実際に逆転した履歴と、採用先を一意に特定できない候補IDの重複を拒否する。

引継ぎのGoal・Context・合意の版を現行記録と照合する。版が変わった場合は再開前に影響を再評価する。レビューの根拠も判断本体と同じ証拠台帳で確認し、参照が切れていたら結論の再評価に戻る。
